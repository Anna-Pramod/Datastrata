# B2 — The verification pipeline Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the four-role verification pipeline that produces a real `verification-result.json` from the real corpus — and nothing downstream of it.

> ## B2 does NOT close the operational signing gate
>
> **B2 builds the agent verification pipeline. It produces real, unsigned verification dossiers, and it cannot sign one.** B3 measures and promotes the pipeline; **B4 is the first phase permitted to verify, adjudicate and sign real CSRD requirements.**
>
> The factory says why, and the ordering is a trust argument rather than a convenience: *"B3 precedes B4 deliberately: the factory is measured before it is pointed at content anyone intends to sign."* The downstream signing machinery being ready is not a reason to reorder that.
>
> **In this revision that promise stops being behavioural and becomes mechanical.** Every B2 dossier carries a pipeline identity that no promotion record mentions, and `verify sign` already refuses an unpromoted `pipelineVersion` with the `unpromoted_pipeline` code (`src/verification/sign.ts`, `src/verification/promotions.ts`). A B2 dossier is therefore **unsignable by construction** rather than unsigned by restraint — and Task 1's teeth check proves it.

**Architecture:** Seven tasks. A pipeline spine carrying role contracts, one capability boundary, run identity and transcript recording; then an earned gap-identity migration to the record contract; then the blind reader, the prosecutors, a second earned migration giving adjudications their own evidence, the adjudicator; then `verify run`, the result writer and a replay-based machinery suite. The deterministic tail consumes agent judgments and computes every pin through the producer the signing path already uses.

**Tech Stack:** TypeScript (strict, ESM), zod, vitest. Agent execution behind an injected runner that the default suite cannot reach.

## Global Constraints

- **`docs/superpowers/TEST-EVIDENCE-STANDARD.md` is normative** — seven failure modes; read before writing any teeth check. A red check is not evidence until its message names the assertion you intended, and a mutation is not evidence until you have confirmed it changed the property you meant.
- **A gate is not tested until its removal from the production path reddens something.** Direct-call tests prove the function; only a run-level test proves the wiring. Every enforcement point introduced by a task must have at least one test that traverses the real production entry point and fails when that enforcement call is removed. **This is failure mode 6 at the call-site level: a thoroughly tested validator is still inert if production never invokes it.** Observed three times in this plan — `sourceShapedGaps` in Task 1, its analogue in Task 2, and both prosecutor gates in Task 3 — each found by nulling a call site and watching a fully green suite.
- **No signing. No ledger writes. No promotion records.** B2 produces dossiers. If a task appears to need a signature to prove something, that is a sign the property belongs to B4.
- **B2 may create verification results only through the sanctioned pipeline.** No hand-authored result file and no manually assembled dossier counts as operational evidence.
- **Do not bulk-produce the requirement library** to make anything look complete. Each real dossier must have evidence that was actually produced and inspected.
- **`npm test` performs no network call and spends nothing**, and that is enforced rather than intended — see Task 1 behaviour 6.
- **`src/verification/` stays pure.** Agent execution, transcript I/O and result writing live in the pipeline and CLI layers.
- **Program-agnostic.** `grep -ri csrd backend/engine/src/` stays at exactly **five**.
- **Commit style:** imperative sentence-case, no prefix, **no `Co-Authored-By` trailer**. **The user runs every `git add` and `git commit`.**
- Baseline: **29 frontend + 909 engine** green, `npm run typecheck` exit 0, `npm run test:standalone` exit 0. Each task's baseline is the previous task's finishing count.

## The boundary this plan exists to hold

Three things must be impossible to confuse:

```
agent judgment   !=   deterministic pins   !=   final validated record
```

**The deterministic tail owns** — and computes for itself — every pin, the evidence validation, the structural and cross-field result consistency, the canonical result hash, and the write. **It consumes rather than invents** the blind reading, prosecutor coverage, prosecutor challenges, and adjudicated verdicts and resolutions.

That split is the factory's own: *"Evidence check → result-schema validation → Markdown render → review sheet. No agent participates."*

## Result-field ownership

**Every field of `verificationResultSchema` has exactly one producer.** This table is the contract Tasks 1–5 implement; an orphan here is a defect in the plan, not a detail for the implementer. Rows marked Task 1.5 or Task 3.5 are the two places B2 changes that contract rather than filling it, each because the first real producer of a field found the record could not state something truthfully.

| Result field | Sole producer | Where |
|---|---|---|
| `packId`, `requirementId` | Run identity | Task 1 |
| `requirementVersion` | Authored requirement `version`, cross-checked against `verification/requirement-versions/<packId>.json` | Task 1 identity, verified in tail (Task 5) |
| `resultSchemaVersion` | Schema literal — `'1.1.0'` after the gap-identity migration, `'1.2.0'` after adjudication evidence | `result.ts`; bumped in Tasks 1.5 and 3.5 |
| `pipelineVersion` | **Pipeline identity builder** — digest over prompt-file hashes, model ids, role config, `resultSchemaVersion`, closure policy | Task 1 |
| `rendererVersion` | `RENDERER_VERSION` constant | `verification/render.ts`, already built |
| `requirementInputSha256`, `conditionSha256`, `renderedConditionSha256`, `corpusClosureSha256`, `corpus[]` | **Shared pin producer** extracted from `currentStateOf` | Task 1 extraction, used by tail (Task 5) |
| `reading.elements[]` | Blind reader | Task 2 |
| `coverage.cells[]` (direction, ids, verdict) | Prosecutors | Task 3 |
| `challenges[].id/lens/statement/evidence` | Prosecutors — **why the challenge was raised** | Task 3 |
| `challenges[].verdict`, `challenges[].resolution`, `challenges[].adjudicationEvidence` | Adjudicator — **why that verdict was reached** | Contract in Task 3.5, produced in Task 4 |
| `coverage.cells[].challengeId` | Deterministic link from an adverse cell to the challenge raised for it | Task 3 emits, tail asserts (Task 5) |
| `openQuestions[]` | **Deterministic projection of `OPEN_QUESTION` adjudications** — never independently authored | Task 4 tail step |
| `gaps[]` | Deterministic closure/corpus machinery, never an agent | Contract in Task 1.5, produced in Task 2 |
| `narrative` | **Human, and explicitly deferred to B4.** B2 never writes it | see below |
| Final validation, canonical hash, write | Deterministic tail | Task 5 |

**Two ownership notes that are decisions rather than bookkeeping:**

**`openQuestions[]` is derived, and that makes the sign gate redundant by construction.** `src/verification/sign.ts` refuses on a challenge verdicted `OPEN_QUESTION` *and* separately on every `openQuestions[]` entry, because a gate reading only the list "would sign over an argument the adjudicator never settled." Deriving the list from the verdicts means the two refusals now always fire together. That is the correct outcome — belt and braces over one truth rather than two lists that can disagree — and Task 4 asserts it rather than leaving it to coincidence. Spec §3.3 permits this: the adjudicator "produces a verdict per challenge", so every open question originates in a challenge.

**`narrative` is deferred, and the deferral is recorded rather than silent.** §3.5 gives the Markdown dossier one human-authored `narrative` block that round-trips back into the JSON. That is a human authoring stage over a *signed-candidate* dossier, and B2 signs nothing. B2 writes results with `narrative` absent (the field is `.optional()`), and **B4 owns the round-trip**. See "Deliberate scope edges" for the Markdown render that carries it.

One consequence B4 should inherit rather than rediscover: `narrative` is inside the canonical result, so writing it **moves `resultSha256`**. The round-trip therefore has to complete *before* signing, not after — a signature taken over a narrative-less result is stale the moment a reviewer writes one.

## Identity semantics across B2, B3 and B4

```
B2  derives a pipeline identity        -> deterministic digest of what actually ran
B3  gives that identity standing       -> promotion record + measured metrics
B4  signs under a promoted identity    -> first real signature
```

The identity is **derived, never chosen**: a digest over the per-role prompt *file* hashes, the exact model identifiers, the role configuration (prosecutor count, lens set, ordering), `resultSchemaVersion` and the closure policy — §5.1's list. `promotions.ts` already anticipates exactly this: the pin is *"a string the run that produced the dossier chose for itself"*, and the promotion ledger is what turns it into a claim somebody stood behind.

Two properties follow, and both are tested:

1. **Same inputs, same identity.** Changing a prompt file, a model id, or the lens set moves it.
2. **B2 writes no promotion record**, so every B2 identity is unpromoted, so `verify sign` refuses with `unpromoted_pipeline`. **This is the mechanical form of the signing gate.**

## One capability boundary, not three role instructions

**Entitlement is constructed once and handed down as a capability.** Spec §3.0 binds reader, prosecutors *and* adjudicator to the entitled closure, and states the invariant it protects:

> Everything the agents were entitled to know is exactly what the signature pins.

Telling each role separately which files it may open makes that invariant three promises that can drift apart, and a prosecutor quietly reading outside the closure would make `corpusClosureSha256` describe a surface the run did not use. So:

- The pipeline builds **one `EntitledClosure`** from the requirement's `sources[]` via `docsForSources` + `computeClosure` (both already built in `src/corpus/closure.ts`), and it is the **only** document accessor any role receives.
- A role receives a *view* backed by that closure. There is no second path to document text in any role input type — not a corpus handle, not a path, not a loader.
- A request for a document outside it does not return text. It produces a gap (below) and **agent verification stops**.

## Three outcome states, never one "refusal"

The plan's earlier wording collapsed distinct outcomes. They are separated here because the built machinery already distinguishes them.

| Outcome | What happened | Result file | Signable |
|---|---|---|---|
| **Complete** | Every role ran; the tail validated the assembled record | **written** | Gate-dependent (and never in B2 — unpromoted identity) |
| **Gap-bearing** | Entitled material was missing or unreachable; agent verification stopped at the gap | **written**, carrying `gaps[]` | **No** — `unresolved_gap` |
| **Invalid** | Malformed agent output, failed evidence check, structural or cross-field inconsistency | **not written** — no partial file | n/a |

**A gap is a recorded verification outcome, not a failure to produce one.** `gapSchema` is a field *in the result*, and `sign.ts` refuses `unresolved_gap` by reading `result.gaps[]`. If B2 never wrote a gap-bearing result, `gaps[]` would have no producer and that refusal would be unreachable — a missing refusal, which is invisible: everything passes.

The wording to use, because "halt and write" reads as a contradiction: **agent verification stops at the gap; the deterministic tail records the gap-bearing dossier and performs no further substantive judgment.** The tail still computes pins and validates structure — a dossier that cannot be parsed is Invalid whatever else is true of it — but it adjudicates nothing and derives no coverage.

### `gap` and `OPEN_QUESTION` mean different things

The two are the plan's only ways of saying "this did not resolve", and collapsing them would make a halted run indistinguishable from a completed one that found genuine legal ambiguity.

```text
gap
  = the verification evidence surface itself is incomplete
  -> discard substantive judgments
  -> record only the deterministic gap-bearing dossier
  -> repair corpus / closure
  -> restart verification from the reader

OPEN_QUESTION
  = the evidence surface is complete, but a proposition cannot be settled from it
  -> retain the completed reading, coverage and challenges
  -> the dossier is whole; it simply does not conclude
```

The asymmetry in what survives is the point. A gap means the run was reading the wrong surface, so nothing produced against that surface can be trusted — and §3.0 forbids topping a reading up, because a repaired run must restart against the new closure. Preserving a reading past a gap would give the dossier a **hybrid provenance**: some judgments formed under the old closure, the rest under the new one, with `corpusClosureSha256` able to describe only one of them. An `OPEN_QUESTION` carries no such problem: the surface never moved.

This is what makes the gap-bearing invariant unconditional rather than conditioned on where the run stopped (Task 2 behaviour 5).

**Both gap classes have producers and tests** (§4.2: collapsing them "would hide exactly the population B3 needs to count"):

| Class | Means | Producer |
|---|---|---|
| `corpus_gap` | The entitled source material is not in the corpus at all | **New code in Task 2** — see the identity problem below. `ClosureEntryNotFoundError` covers only one of the two shapes |
| `closure_gap` | The material exists in the corpus, but traversal policy did not entitle the reader to reach it | The `EntitledClosure` view, when a role requests a `docId` the corpus holds and the closure excludes |

### The gap identity problem — decide before Task 2

`corpus_gap` has **two shapes**, and the built machinery covers only the first:

| Shape | Example | Existing producer |
|---|---|---|
| A named document is absent from the index | closure entry `DOC-X` not in `index.json` | `ClosureEntryNotFoundError` — **built** |
| `sources[]` resolve to **no document at all** | `CSRD-S-012` → `SRC-005/006/007`, none served | **none** |

The second shape is unreachable from the existing path: `docsForSources` iterates the index and returns only documents it *found*, so it can never hand `computeClosure` a docId to reject. Measured, not assumed:

```
docsForSources(index, [SRC-005, SRC-006, SRC-007])  ->  []
computeClosure(index, [])                           ->  does NOT throw
                                                        docIds [], edgeIds [],
                                                        sha256 e3b0c44298fc...
```

`e3b0c442…` is the SHA-256 of the empty string. **Left alone, a `CSRD-S-012` dossier would pin the empty digest as `corpusClosureSha256`** — silently asserting a computed entitlement over nothing, which is precisely the failure `ClosureEntryNotFoundError` exists to prevent one document at a time.

Two consequences, and the second needs a decision:

1. **An empty closure must never appear unaccompanied.** The digest is faithful — the entitled set really is empty — so the fix is not to refuse computing it, which would leave the required `corpusClosureSha256` unfillable for exactly the dossier that needs it. The fix is that an empty closure with an empty `gaps[]` is unrepresentable (Task 2 behaviour 6).
2. **`gapSchema.docId` cannot express this shape.** It is a required string, and what is missing here is `SRC-005/006/007` — *source* ids, not document ids. **Decided: evolve the gap contract (Task 1.5).** Putting a `SRC-###` value in a field named `docId` was considered and **rejected**: the machine-readable field would say "document id" while `detail` explained it was really a source id, leaving prose to correct the structured record. That is the semantic debt `.strict()` exists to prevent, and it would leave the original bug expressible while adding a field that was supposed to fix it.

**This is the cheapest possible moment to find that B1b's shape cannot represent a real B2 state:** no authoritative result exists and nothing is signed. Freezing a schema should prevent casual churn, not force knowingly false data when the first producer meets a state the schema cannot express.

## Corpus preconditions — measured, not assumed

Two facts were established against the real corpus before this revision, and both change what B2 can honestly claim.

**1. `CSRD-S-012` is the only requirement with no entry document.** Its `sources[]` are `SRC-005/006/007`; the corpus serves only `SRC-001` and `SRC-004`. It must surface as a real `corpus_gap`. **Do not weaken the reader or the closure to make it produce something.** The gap is the finding.

**2. Every other requirement has an identical entitled closure**, and this is the constraint that shapes Tasks 2, 3 and 5:

```
15 of 16 requirements -> docs [DOC-32013L0034, DOC-32026L0470], 1 edge,
                         corpusClosureSha256 ef2e7a8c1312... (identical for all)
```

Reverse structural traversal works correctly — an amending-directive-only entry reaches the consolidated text through `amendedBy` — so the closure is not too *narrow*. It is that the corpus holds two documents and one edge, so the entitled closure is the entire corpus for every requirement. Three consequences must be stated in the plan rather than discovered in a task:

- **`closure_gap` cannot occur against the real corpus.** There is no document outside any closure. Task 2 must therefore test it against a **synthetic fixture corpus** built for the purpose, and must not claim the real corpus exercises it.
- **"The reader reads only the entitled closure" is vacuously true against the real corpus** — failure mode #5. Any teeth check for entitlement must use the fixture corpus, where a document exists that the closure excludes.
- **`sources[]` currently has no discriminating power over the evidence surface.** §3.1's provenance-defect property — a requirement whose `sources[]` omits the act that proves it wrong is still caught, and the omission is reported against `sources[]` — **cannot be demonstrated in B2**. It is recorded here as a B3 benchmark property awaiting a richer corpus, not quietly claimed.

## Deliberate scope edges

**The Markdown render and review sheet.** §3.4's tail is "Evidence check → result-schema validation → Markdown render → review sheet." The review sheet exists (`src/cli/review-sheet.ts`, B1b). The **Markdown dossier renderer does not exist**, and it carries the `narrative` round-trip. B2 builds neither: the dossier is a human review surface over a signable candidate, and B2 produces nothing signable. **Both are assigned to B4**, with `narrative` (see the ownership table). This is a deferral with a named home, not an omission.

**One live agent run.** Task 5 records transcripts for one real requirement, which requires real spend outside `npm test`. That run is B2's only live execution and its output is committed as fixtures; everything thereafter replays.

## Why a human assembler was rejected

It would create a second production route to the authoritative result, and `pipelineVersion` — which resolves to per-role prompt hashes, model identifiers, role configuration, schema version and benchmark identity — would become ambiguous. Either a human procedure gets called a pipeline version, weakening the field, or a second provenance concept and a second signing path appear that the factory never designed. Neither is warranted to reach a signature sooner.

### Task 1: The pipeline execution contract, capability boundary and transcript record

Infrastructure and every cross-task contract. **No judgments, real or fake.** Tasks 2–5 implement against what this task establishes, so a contract wrong here is a contract Tasks 2–5 must break or wrap.

**Produces:**
- `AgentRole<I, O>` with `run(input: I): Promise<RoleExecution<O>>`
- `RoleExecution<T>` carrying `output`, `transcript`, `model`, `promptSha256`
- **`EntitledClosure`** — the single capability object every role's document access is backed by
- **Prompt files on disk**, one per role, and `promptSha256` computed *from the file*
- **The pipeline identity builder** producing `pipelineVersion`
- **The shared pin producer**, extracted from `currentStateOf`
- A **verification run identity** — what distinguishes one run from another and what a transcript belongs to
- A transcript schema and its storage layout
- Orchestration: reader → prosecutors → adjudicator → deterministic tail
- An **injected agent runner** the default suite cannot reach

**Required behaviours:**

1. **Role outputs are typed and validated at the seam.** An agent returning malformed structure fails at its own boundary, named, rather than surfacing later as an invalid result.
2. **Every execution records `model` and `promptSha256`.** These are `pipelineVersion` inputs (§5.1); a role that cannot say which prompt and model produced it cannot be measured by B3.
3. **Prompts are version-controlled files, and `promptSha256` is the hash of the file.** Not a hash of an inline string, and not metadata supplied alongside one. §5.1 pins *per-role prompt file hashes*; an identity that pins something the repository cannot independently reproduce is a claim, not a pin. A prompt assembled at runtime from a file plus interpolated inputs hashes **the file**, and the interpolated inputs are transcript content.
4. **`pipelineVersion` is derived, never passed in.** A digest over per-role prompt-file hashes, model identifiers, role configuration, `resultSchemaVersion` and the closure policy. Same inputs → same identity; any one of them moving → a different identity. **No promotion record is written, by anything, ever, in B2.**
5. **One shared pin producer, extracted rather than reimplemented.** `src/verification/current-state.ts` already computes `requirementInputSha256`, `conditionSha256`, `renderedConditionSha256`, `corpusClosureSha256` and `corpus[]`, and its header records why a second construction is a defect: three surfaces each built it themselves and *"a third would have made 'the site and the review sheet agree about this signature' a coincidence rather than a property."* Extract the **result-independent** subset into one producer; `currentStateOf` becomes that producer plus `resultSha256`, and B2's tail calls the same producer. `resultSha256` stays outside it because it is necessarily post-assembly — the result does not exist when its pins are computed.
   **Why this is load-bearing and not tidiness:** `src/cli/sign.ts` builds its candidate entry from these same helpers, and candidate consistency compares a result's pins against it. Two constructions that drift make `verify sign` refuse every dossier B2 produces, with `candidate_inconsistent`.
6. **The default suite cannot reach a live runner, and that is enforced.** Injection alone is insufficient if a live runner stays importable and callable under ordinary vitest. Required: a separate live entrypoint behind an explicit capability gate (environment token or equivalent), a `test:agents` script distinct from `npm test`, and the default suite excluding the live path. **A run with no replay runner supplied fails before performing network I/O**, loudly and by name, rather than silently spending money.
7. **The deterministic tail is a separate module with its own interface**, consuming role outputs and computing every pin through the shared producer. It must not accept a pin from an agent.
8. **Transcripts are recorded for every role**, sufficient to replay the run with no network. **They live under `backend/engine/test/`**, which the artifact hygiene guard already forbids in the deployable artifact (`scripts/standalone-harness.mjs`, `backend/engine/test/**`) — so the "not a runtime input" property is enforced by a guard that already exists rather than by placement convention.

**Teeth check — hostile pins, two layers.** The single-layer version of this check was contradictory: if a role output type structurally excludes pins you cannot construct the hostile value, and if you can construct it the type does not exclude them. Both layers are required.

```text
compile boundary:
  role output carrying an authoritative pin  -> does not typecheck

runtime hostile-object boundary:
  force a pin-bearing object through `unknown`
  -> seam validation strips or rejects it, or the tail ignores it
  -> the tail-computed pin is what lands

mutant:
  mutate the tail to trust the hostile supplied pin
  -> the exact-pin assertion fails, naming that pin
```

Confirm the mutation landed before believing the red (failure mode #2). A pipeline that accepts an agent-supplied pin has no integrity story at all.

**Teeth check — the identity is derived, and one input at a time.** Vary **exactly one** identity input per case — a prompt file's bytes, one model id, the prosecutor count, the lens set, the closure policy — and confirm each moves `pipelineVersion`, and that varying none leaves it byte-identical. One case per input, because a builder that hashes only the lens set passes a test that changes several at once.

**Teeth check — unpromoted by construction.** Take a derived identity to `isPromoted` against an empty promotion ledger and confirm it is unpromoted. Positive control: with a promotion record for that exact identity present, `isPromoted` answers true — proving the answer tracks the record rather than being unconditionally false. **B2 keeps no such record**; the control is constructed in the test and discarded.

> **Scope note.** The full check — a complete dossier taken to the sign gate and refused with `unpromoted_pipeline` — belongs to **Task 5**, which has real role outputs. Task 1 produces no judgments, real or fake, so it cannot assemble a dossier to refuse. Task 1 proves the identity property; Task 5 proves the refusal it causes.

**Teeth check — no live call from the default suite.** A negative observation needs something observing, or it passes because nothing ever ran (failure mode #7). Install a network trap for the duration of the test — a `fetch`/undici interceptor that records and throws — then run the machinery path with no replay runner and assert **both** halves: the named failure arrived, **and** the trap never fired. Then mutate the guard to fall back to a live runner and confirm the trap fires and the test fails naming the network call.

### Task 1.5: The gap identity migration

**A schema evolution, earned rather than casual.** B2's first producer found a real verification outcome that the B1b record cannot state truthfully: a requirement whose `sources[]` are served by no document has no missing *document* identity to name. This task corrects the record before anything is signed over it. **Task 1 does not depend on it** — pipeline identity, entitlement, prompt provenance, transcripts and the shared pin producer are all indifferent to how a source-level gap is encoded — so it sits between Task 1 and Task 2, and Task 2 cannot begin without it.

**The ontology being installed.** Three genuinely different populations, which B3 can then measure separately:

| Shape | Means |
|---|---|
| `corpus_gap` + `sourceId` | Source-register / corpus-coverage defect: nothing serves this source |
| `corpus_gap` + `docId` | An expected document is absent from the corpus |
| `closure_gap` + `docId` | The document exists, but entitlement traversal did not reach it |

**Required behaviours:**

1. **Structural form: optional fields, not a union.** `gapSchema` becomes

   ```ts
   { kind: 'corpus_gap' | 'closure_gap', docId?: string, sourceId?: string, detail: string }
   ```

   **A `z.discriminatedUnion` at the element level is not an option here, and the reason is recorded in the code:** the accounting walker takes its path set from the runtime zod schemas and **fails closed on an unrecognised node kind**, and `result.ts` carries a standing note forbidding refinements because a wrapped composite would emit one row while every field beneath it went unaccounted. Optional fields stay individually visible to the walker; `ZodOptional` is already a kind it handles.

2. **Cardinality and kind semantics live in `assertResultConsistency`**, which is where every other cross-field rule already lives:

   ```text
   corpus_gap   -> exactly one of docId / sourceId
   closure_gap  -> docId required, sourceId absent
   ```

   This is the established two-stage split: structure the walker can see, semantics the consistency pass enforces. Every problem collected before throwing, as the rest of that function does.

3. **A source id may not masquerade as a document id.** Adding `sourceId` while leaving `docId: 'SRC-005'` expressible would install the new field and keep the original bug. Cross-check identifiers against the registry they belong to — the corpus index for `docId`, `sources.json` for `sourceId` — so the distinction is enforced rather than merely available.

4. **`resultSchemaVersion` bumps to `1.1.0`.** `pipelineVersion` includes `resultSchemaVersion` (§5.1); if the schema changes while the literal holds, two structurally different factories claim one schema identity. The literal in `result.ts` is what rejects a future shape, so it must move with the shape.

5. **`result.gaps[].sourceId` gets a field-accounting row.** The walker fails in both directions, so an unclassified new path fails the suite — which is the guard working. Classify it alongside `result.gaps[].docId` (`['display', 'audit']`) unless the review finds it exercises different authority.

6. **Update `sign.ts`'s refusal message** to name whichever identifier the gap carries. `unresolved_gap` is the only consumer of `gaps[].docId` in `src/`.

**Blast radius, measured.** `resultSchemaVersion` appears 13 times across `verification-result`, `verification-sign`, `verification-accounting`, `cli-sign`, `cli-review-sheet` and `frontend/web/test/fixture-repository.ts`. Result-gap fixtures with `docId` live in `verification-sign.test.ts` and `verification-result.test.ts`. **Do not touch `assess.ts:74`, `checkResponse.ts:150` or `migration-golden.test.ts:214`** — those are engine *determination* gaps, an unrelated concept that merely shares the word. The review sheet does not render result gaps.

**This is an intentional migration, not a regression.** Updating the version-sensitive tests and goldens is the work; record in the commit message why the schema moved and what it could not previously say.

**Teeth check — the semantic lie is now unrepresentable.** The full validity matrix, each case asserted separately:

```text
corpus_gap  + sourceId SRC-005          -> valid
corpus_gap  + docId DOC-X               -> valid
closure_gap + docId DOC-Y               -> valid

closure_gap + sourceId SRC-005          -> invalid
gap with both docId and sourceId        -> invalid
gap with neither                        -> invalid
corpus_gap  + docId "SRC-005"           -> invalid   <- the original lie
```

### Task 2: The blind reader

Spec §3.1. **Blind to the encoding** — it reads the law and reports what it says, without seeing the `Condition` it will later be compared against.

**Required behaviours:**

1. **The reader's input is a positive projection, never `Omit<>`.** Construct a `ReaderInput` type containing only what §3.1 entitles it to: the requirement's identifiers and provision citation, and the `EntitledClosure` view. An `Omit<AuthoredRequirement, …>` silently admits every field added to the requirement later, so blindness would decay without a single edit to this task's code.
   **Excluded, and each named because §3.1 names it:** `condition`, the rendered English, `plainEnglish`, `caution`, customer facts, obligation templates, any prior reading — and `backend/engine/verification/CSRD-S-001.md`, the hand-written review log that contains the exact Omnibus I finding the pipeline exists to rediscover independently.
   Blindness is the property that makes the comparison meaningful; if the reader can see the answer, coverage agreement proves nothing. **Enforce it in the input type, not by instruction.**
2. **Document access is the `EntitledClosure` view and nothing else.** The reader holds no corpus handle and no path.
3. **Every reading element carries evidence**, and `absence` may never be the sole evidence for one. This restates at the role boundary the rule `assertResultConsistency` already enforces at the record boundary — a second gate over one rule, not a second rule. Task 5 asserts the two agree.
4. **Both gap classes are produced and distinguishable**, in both of `corpus_gap`'s shapes (see "The gap identity problem"). Agent verification stops at the gap and the tail records a gap-bearing dossier (see "Three outcome states").
5. **A gap-bearing dossier has a canonical shape, and it is not an absent reading.** `reading`, `coverage`, `challenges` and `openQuestions` are all **required** by the schema, so "the reading is absent" is not representable and must not be attempted. The truthful record is the required containers **canonically empty**, with `gaps[]` carrying the explanation:

   ```json
   { "reading": { "elements": [] }, "coverage": { "cells": [] },
     "challenges": [], "openQuestions": [], "gaps": [ ... ] }
   ```

   The meaning is explicit: **no agent judgment was successfully produced, the judgment-bearing containers are therefore canonically empty, and `gaps[]` says why.** That is more truthful than a record implying the reader returned an empty legal reading.

   **Enforce it as a cross-field invariant, not prose.** Add to `assertResultConsistency`:

   ```text
   gaps.length > 0  =>  reading.elements == []  and  coverage.cells == []
                        and challenges == []    and  openQuestions == []
   ```

   The rule is unconditional on *where* the run stopped, and deliberately so — the record carries no field saying where it stopped, so a condition on that would be unenforceable. It is also correct rather than merely convenient: §3.0 states that a reading produced under a narrower entitlement **cannot be topped up** and that the run restarts once the gap is filled. So a gap-bearing dossier never carries partial judgment, whichever role hit the gap. A completed run that merely wished for another document has an `OPEN_QUESTION`, not a gap.

   **This rule lands in Task 2**, which is the phase that produces gaps; Task 1.5 shipped the gap identity contract and is not reopened for it.

6. **An empty closure is only ever valid accompanied.** `computeClosure(index, [])` returns the empty-string digest `e3b0c442…` rather than throwing. That digest is a *faithful* hash of a genuinely empty entitled set, so the rule is not "never compute it" — a gap-bearing dossier still has to fill `corpusClosureSha256`, and there is no other value it could carry. The rule is that **an empty closure without a populated `gaps[]` is unrepresentable**: the tail refuses to write a result whose closure is empty and whose `gaps[]` is *also* empty, and the pairing is asserted, not assumed. Unaccompanied, `e3b0c442…` is a dossier claiming an evidence surface it never had; accompanied, it is the honest record of a requirement whose sources serve nothing.

**On `CSRD-S-012`:** its `sources[]` resolve to **zero** corpus documents. It must surface as a real `corpus_gap` under the decision recorded above. **Do not weaken the reader or the closure to make it produce something.** The gap is the finding.

**On testing `closure_gap`:** it **cannot** be exercised against the real corpus, where all 15 non-gap requirements share one closure covering every document that exists. Build a **synthetic fixture corpus** — at minimum three documents where one is reachable only beyond the reference-depth bound — and test `closure_gap` there. Do not report the real corpus as evidence for this path.

**The fixture corpus runs the real machinery.** It is a different `index.json`, not a different code path: it goes through the same `docsForSources`, `computeClosure` and `CLOSURE_POLICY_V0` the production path uses. A hand-rolled stand-in would make these tests prove things about test code — the exact substitution `test/corpus-closure.test.ts` already avoids.

**Teeth check — the gap classes are genuinely distinct.** Against the fixture corpus, produce a `corpus_gap` and a `closure_gap` and confirm each names its own kind and `docId`. Then mutate the closure machinery to report both as `corpus_gap` and confirm a test fails naming the collapse. Positive control: a requirement whose material is fully entitled produces **no** gap — otherwise "always gaps" passes both halves.

**Teeth check — entitlement is enforced, not requested.** Against the fixture corpus, have the reader request a document the corpus holds and the closure excludes, and confirm it receives no text. Confirm the same run's `corpusClosureSha256` does not cover that document — the two together are the §3.0 invariant.

**Teeth check — blindness is structural.** Confirm a reader input carrying the condition, `plainEnglish`, `caution` or the rendered English **fails to compile**. ### Task 3.5: Adjudicated challenges carry their own evidence

**The second earned schema evolution, and the same discovery as the first.** Task 4's producer found another proposition the record cannot state truthfully. §3.3 binds every adjudicated verdict to `evidence[]`, but `challengeSchema` carries exactly one evidence array and the ownership table gives it to the prosecutors. So the record can say *why a challenge was raised* and cannot say *why it was adjudicated the way it was*.

Those are different propositions:

```text
challenge.evidence              "There is something here worth challenging."
challenge.adjudicationEvidence  "Here is why that challenge is confirmed,
                                 rejected, or unresolved."
```

One array cannot truthfully stand for both unless ownership is redefined, which would undo the one-producer discipline.

**Seam-only was rejected.** Binding the adjudication's evidence at the role boundary and leaving it in the transcript is not merely reduced auditability — it changes the meaning of the signed artifact. The transcript answers *what did the model receive and produce*; `verification-result.json` is what is hashed and signed. A fact necessary to justify an adjudicated regulatory conclusion belongs in the latter. Both provenance layers are kept; neither substitutes for the other.

**The name is `adjudicationEvidence`, not `resolutionEvidence`.** `OPEN_QUESTION` has no resolution, yet §3.3 still requires its verdict to be evidence-bound — and `OPEN_QUESTION` must never mean "the adjudicator had no evidence". It means the evidence available was sufficient to establish that the record cannot settle the challenge, which is precisely what B4's human inspects.

**Required behaviours:**

1. **`adjudicationEvidence: z.array(evidenceItemSchema).min(1)` on `challengeSchema`** — required for **all three** verdicts. No refinement, so the accounting-walker constraint holds.
2. **The existing semantic rules stand, with one addition each:**

   ```text
   CONFIRMED       -> non-blank resolution   + adjudicationEvidence >= 1
   MISMATCH        -> non-blank resolution   + adjudicationEvidence >= 1
   OPEN_QUESTION   -> resolution absent or non-adjudicated, as now
                                             + adjudicationEvidence >= 1
   ```

3. **`resultSchemaVersion` bumps `1.1.0` → `1.2.0`.** `pipelineVersion` pins it, so the schema identity moves with the contract. Do not add the field silently under `1.1.0`.
4. **`result.gaps[]`-style accounting applies**: `result.challenges[].adjudicationEvidence` gets a `FIELD_ROLES` row. The walker fails in both directions, so an unclassified path fails the suite — observe that red before classifying.
5. **Sole `absence` is rejected**, as everywhere else evidence is bound.

**Teeth check — evidence attribution, not "some evidence somewhere".** Use *deliberately different* evidence in the fixture; if both arrays hold the same quote a field-crossing bug is invisible.

```text
prosecutor evidence = E-P
adjudicator evidence = E-A
final challenge:  evidence == E-P  and  adjudicationEvidence == E-A
```

Then four mutants:

```text
copy prosecutor evidence into adjudicationEvidence   -> red
drop adjudicationEvidence                            -> structural red
adjudicationEvidence of only absence items           -> evidence-binding red
remove the validation from the production path       -> run-level red
```

The last is the call-site rule; without it the rule exists and does not run.

**This is a prerequisite, committed separately.** Task 5 must assemble and validate a contract whose ownership is already settled; deciding what an adjudicated challenge means while implementing the writer is the late-schema-discovery pattern Task 1.5 exists to prevent.

### Task 5: `verify run`, the result writer, and the machinery suite

The deterministic tail end to end, plus the suite that makes all of it testable without spending anything.

**Required behaviours:**

1. **`verify run` is a subcommand of the existing CLI, not a parallel executable.** `npm run verify` already carries the grammar `sign | revoke | sheet` (`src/cli/verify.ts`); this adds `run` to it, dispatching to a `runVerify` that returns a `CliOutcome` like its siblings, with its exit codes in `exit-codes.ts`. A second entry point would be a second production route to the authoritative dossier — the thing this plan rejected a human assembler for.
2. **The tail computes every pin through the shared producer** (Task 1 behaviour 5) and validates before writing. `parseVerificationResult` — structural *and* cross-field — must pass, or nothing is written.
3. **The three outcome states are implemented as three states**, per the table above: Complete writes, Gap-bearing writes with `gaps[]` populated and stays unsignable, Invalid writes nothing at all. They must never collapse into one "refusal" concept.
   **Each maps to an exit code, and the mapping is decided here rather than invented in code.** `exit-codes.ts` is the contract (`EXIT_OK`, `EXIT_REFUSED`, `EXIT_INTEGRITY_FAILURE`, `EXIT_FORENSICS_REQUIRED`, `EXIT_USAGE`):

   | Outcome | Exit | Why |
   |---|---|---|
   | Complete | `EXIT_OK` | The run produced the dossier it set out to produce |
   | Gap-bearing | `EXIT_OK` | **Also success.** `run` records what it found; refusing to sign it is `sign`'s job, and reporting a gap as a failed run would make "we could not read the law" indistinguishable from "the machinery broke" |
   | Invalid | `EXIT_REFUSED` | Nothing was written, and the reason is named |

   A gap is a finding, not an error. Collapsing it into `EXIT_REFUSED` would hide from B3 exactly the population §4.2 asks it to count.
4. **The machinery suite replays recorded transcripts**, is deterministic, blocks commits, and makes no network call. This is §5.2's `verification-machinery`; the live path is `test:agents` and never blocks a commit.
5. **Determinism is a property of the machinery, not the agents.** Same transcripts in, same canonical result hash out. Agent variability is B3's subject, not something to suppress here.
6. **Transcripts and fixtures stay out of the deployable artifact.** `verification/*/*/verification-result.json` is a **declared runtime input** (`frontend/web/verification-runtime-inputs.mjs`, member `pinned-verification-results`, `onAbsence: 'fatal'`), so Task 5's first real result *ships*.
