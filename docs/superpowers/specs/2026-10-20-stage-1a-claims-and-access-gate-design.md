# Stage 1a design: truthful status language and a temporary access gate for configured profiles

**Status:** increment design for the first bounded implementation under the accepted revision 2 of `2026-10-20-commercial-platform-proposal.md` (§8, increment 1a). Authorised 2026-10-20 for implementation and verification only: no public deployment, live communications, paid services, legal signing, promotion or regulatory capture. Written 2026-10-20; the plan is `docs/superpowers/plans/2026-10-20-stage-1a-claims-and-access-gate.md`.

**Scope:** `frontend/web` only. No engine file changes (`grep -ri csrd backend/engine/src/` stays at 7). No persistence, no accounts (those are increments 1b to 1d). The SAP profile, the frozen evidence and `b1b-record` are untouched.

## 1. Outcome

A visitor can no longer read a claim the record does not back, and a direct request cannot obtain a configured profile unless it carries a valid access session issued from a server-side secret. Authorised local access still works. The contact form appears only where delivery is already configured.

## 2. The access gate

**Where it applies.** Everything under `/dashboard` (the page, its React Server Component payload requests and any future data route under that path) and the only place a configured profile is read, `lib/record.ts`, which is reached solely through `/dashboard`. The gate is enforced twice, independently:

1. `middleware.ts` (matcher `/dashboard/:path*`) refuses before any rendering and sets the cache headers on every response for those paths.
2. `app/dashboard/page.tsx` calls the same pure guard before `pilotRecord()`; if the guard denies, the page renders a refusal without reading the profile. A middleware that is absent or misconfigured therefore still cannot leak the profile.

Both call one pure module, `lib/access.ts`, which takes the environment, the request's cookies, the request time and the protocol, and returns a decision. It reads no clock itself and performs no I/O, so it is unit-tested directly.

**Configuration, and denial when it is missing or invalid.** `DATASTRATA_PILOT_ACCESS_SECRET` (server-side only, never `NEXT_PUBLIC_`) is the passphrase an operator hands to the person who may look. `readAccessConfig(env)` accepts it only when it is set, not blank after trimming, and at least 16 characters; otherwise every request under `/dashboard` is refused with status 503 and the text "Pilot access is not configured", followed by each problem on a line of its own, stated by variable name and never by value (final review, 2026-10-21: a bad revocation setting was reported as a missing secret while the 503 was one fixed sentence), and the profile is never read. The page's own list of the same problems is the second enforcement point's refusal, shown when the middleware is absent. The gate never falls open and never substitutes the synthetic profile for a refusal: the synthetic document, like a configured one, is behind the gate.

**The session.** Submitting the passphrase on `/pilot-access` (a public page) posts to `POST /api/pilot-access`. The handler compares the submitted value with the configured secret in constant time with Web Crypto alone (an HMAC of the secret under a fresh random key, checked against the submitted bytes with `subtle.verify`, so neither length nor content leaks through timing and no Node-only API is needed), issues a token on success and sets it as the cookie `ds_pilot_access`. The token is `v1.<issuedAt>.<expiresAt>.<nonce>.<signature>`: the signature is HMAC-SHA-256 over the first four fields with a key derived from the secret (`HMAC(secret, "datastrata-pilot-access-v1")`), so the passphrase itself is never the signing key, and neither the cookie nor any response carries it. Verification (`verifyAccessToken`) recomputes and compares the signature with Web Crypto's `subtle.verify` (constant time, available in both the Edge and the Node runtime), then checks the expiry and the revocation instant against the request time. Nothing about the session is stored on the server.

- **Expiry:** 12 hours from issue, absolute, carried in the token and checked server-side; the cookie's `Max-Age` matches but is not relied on. No sliding renewal: a longer look means signing in again.
- **Revocation:** three ways. Rotating `DATASTRATA_PILOT_ACCESS_SECRET` invalidates every token at once, because the signing key derives from it. Setting `DATASTRATA_PILOT_ACCESS_REVOKED_BEFORE` to an ISO-8601 instant refuses every token issued before it, without changing the passphrase. An instant later than the request time is refused as configuration (503 naming the variable, no cookie issued), because a session issued under it would be refused as revoked until the instant passed; an equal instant is valid, so sessions issued at it are allowed and earlier ones revoked (final review, 2026-10-21). `POST /api/pilot-access/sign-out` clears the cookie on that browser (the token itself stays valid until expiry or revocation, and the page says so).
- **Cookie handling:** `HttpOnly`; `SameSite=Strict`; `Path=/dashboard` (the token travels only to the protected path); `Max-Age=43200`; `Secure` whenever the request is HTTPS or `NODE_ENV` is production, omitted only for plain-HTTP loopback use so the local look keeps working. The cookie carries only the token.
- **Shared caching:** the middleware sets `Cache-Control: private, no-store` and `Vary: Cookie` on every response it answers for `/dashboard` paths, and on the allowed pass-through. Its refusals reach the client with them (Next adds `Accept-Encoding` to `Vary` where it compresses). On an allowed request, though, the response the client receives is the page's: Next's dynamic rendering answers with its own `Cache-Control: no-store, must-revalidate` and its own `Vary` list, without `private` or `Cookie` (observed in the configured demonstration of 2026-10-21). `no-store` keeps every cache, shared or private, from storing the record, which is the property the gate needs; the pass-through headers are not what proves it. `/pilot-access` and the API route are `force-dynamic` and send `Cache-Control: no-store` (the page `no-store, must-revalidate`). The dashboard page remains `force-dynamic`.
- **Refusals:** a request without a valid session is redirected (303) to `/pilot-access` when it accepts HTML, and answered 401 with a JSON body otherwise; a 503 when unconfigured; the response body never contains the secret, a token or a profile fragment. A refused sign-in follows the same rule: a script gets 401 (wrong or missing passphrase), 429 (limited) or 503 (unconfigured) with a one-key JSON body, and a browser gets a relative 303 back to `/pilot-access?reason=refused`, `limited` or `unconfigured`, so a form post never ends on a blank page. The page turns each reason into a sentence from a fixed map and never echoes the query string.
- **Guessing:** the handler rate-limits failed attempts, 5 in 15 minutes, answering 429 after that, under **one shared key**, `'local'`. No client address is used. On a loopback server every request arrives from 127.0.0.1, and `X-Forwarded-For` holds whatever the client writes, so a key derived from it would let a guesser escape the limit by changing the header on each attempt. A per-client key needs a trusted proxy that sets the address itself; Stage 1a configures none, so no address header is read. The cost of the shared key is a stated limitation (§5): five wrong attempts from anyone refuse everyone, the authorised person included, for up to fifteen minutes. The limiter is in-process memory, adequate for a single local process, and it starts empty whenever the process restarts or the dev server reloads the route. Attempts take turns on it: the comparison is asynchronous, so simultaneous attempts would otherwise all be let in before any was charged, and twenty guesses sent together were all compared in the first implementation. An attempt refused for the limit or for the configuration is not counted, so the lock lasts the fifteen minutes stated and is not extended for as long as someone keeps trying. Failures are logged by status only, never with the submitted value.
- **Navigation:** the public "See a sample report" link on the landing page and the "See how this is maintained" link on the check result are removed; the topbar gets a "Sign out" control on the record page and on the refusal for a profile that cannot be served, the two pages rendered for a verified session.

**Why this and not more.** A stateless signed token is the smallest mechanism that meets the requirements without a user store; it is explicitly temporary, replaced by database sessions and accounts in increment 1c. The two independent enforcement points mean neither a routing change nor a middleware regression can expose the profile.

It runs against the user's own dev server, which is never started, stopped or restarted by the implementer. ## 5. Limitations stated

The rate limiter is per process and has one shared bucket: five failed attempts from anyone lock out everyone, the authorised person included, for up to fifteen minutes, and a per-client limit waits for a trusted proxy that sets the client address (a header the client writes is never trusted); Next.js normalises a loopback request address to `localhost` in a middleware redirect, so with the dev server bound to `127.0.0.1` a refused browser that came in on `http://127.0.0.1:3000` is sent to `http://localhost:3000/pilot-access`; cookies belong to the host that set them, so the session must be signed in on the host the browser then uses (the route handlers answer with relative locations, which keep a browser on its host); the sign-out cannot revoke a token on other browsers (revocation is by secret rotation or the revoked-before instant); the gate is temporary and is replaced by accounts in increment 1c; the "monitored" status cannot be earned until Stage 3's scanner exists; the contact form stays hidden until an inbox is configured by the user.

The signing key is one fast HMAC over the passphrase, and the passphrase is handed to the participant, so whoever obtains a session token can test passphrase guesses offline, outside the rate limiter: a generated random secret is Stage 1a's mitigation, and stronger derivation (PBKDF2 through `subtle.deriveBits`, or a separate server-only signing key) belongs to increment 1b or 1c. Whoever holds the passphrase can mint tokens of any lifetime and issue time, so the 12-hour expiry and the revoked-before instant bind the tokens the server issues, and against a passphrase holder only rotating the secret revokes, which grants nothing that signing in again would not; for the same reason a validly signed token whose issue time is after the request time is accepted, since only a secret holder can mint one. Loopback cookies are not scoped by port (RFC 6265 §8.5) and SameSite ignores ports, so any other server the user runs on `localhost` or `127.0.0.1` receives `ds_pilot_access` on its own `/dashboard` paths and could log it.

A page on any other site can post a form to the loopback port: it can spend the shared limiter's five failures, which locks everyone out for fifteen minutes, or sign a browser out, and `SameSite` does not stand in the way, because the sign-in post carries no cookie and the sign-out needs none (checking `Sec-Fetch-Site` could narrow it later). A local `next start` runs in production mode, so the session cookie carries `Secure` even over plain HTTP, which Safari may refuse on loopback; the local look uses `next dev`, or HTTPS. The dashboard page's own refusals, which render only when the middleware is absent, are HTTP 200, so they rely on Next's dynamic-rendering cache headers (`force-dynamic`) rather than on a refusal status; whenever the middleware runs, every `/dashboard` response, refusal or not, carries its `private, no-store`.
