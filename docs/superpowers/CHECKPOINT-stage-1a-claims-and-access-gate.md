## What was found

Design §3 lists every surface. The first claims scan was case-sensitive, and the landing page's illustration still printed "YOU ARE CURRENT" in capitals (found in the parent's review of Task 6).
- **No gate.** `/dashboard` served whatever profile `DATASTRATA_PILOT_PROFILE` named to anyone who could reach the port.
- **Found while building the gate.**
  - Next normalises a loopback request URL to `localhost` in `NextRequest.url`, so a middleware redirect from a server bound to `127.0.0.1` names `localhost`, a different cookie host. The route handlers answer with relative `Location` headers instead.
  - The first sign-in implementation compared every attempt in a burst: twenty wrong passphrases and the right one, sent together, were twenty 401s and a 303, because the comparison is asynchronous and no attempt had been charged to the limiter before the others passed it. Attempts now take turns: the same burst is five 401s and sixteen 429s.
  - The exported middleware had no behavioural test (Task 2's review): a fail-open body or a frozen clock passed all 46 tests.
- **Found by the final whole-change review** (opus, `sdd/final-review-report.md`: 0 Critical, 2 Important, 11 Minor, "With fixes"):
  - **I1:** the middleware's 503 always said "Set DATASTRATA_PILOT_ACCESS_SECRET.", so a blank or malformed revocation instant was reported as a missing secret, and nothing else named the real problem.
  - **I2:** the signing key is one HMAC over the passphrase, which is handed to the participant. A captured session token therefore allows offline guessing of the passphrase, outside the rate limiter, and a passphrase holder can mint tokens of any lifetime.
  - **D14:** a revocation instant later than the server's clock refused every session issued before it, new ones included: sign-in appeared to succeed and the dashboard sent the browser back.
  - Documentation that no longer matched the code, five leftover phrases that still implied watching or maintaining, and a printed count (`packStats().signed`) that no test could fail on.

## What was decided

- **The gate (design §2).** One pure decision module (`lib/access.ts`) and two independent enforcement points: the middleware before any rendering, and the dashboard page again before it reads the profile (`gatedRecord` is handed `pilotRecord` and calls it only when the decision allows). A stateless HMAC-SHA-256 token, `v1.<issuedAt>.<expiresAt>.<nonce>.<signature>`, under a key derived from the secret; 12 hours absolute; revocation by rotating the secret or by `DATASTRATA_PILOT_ACCESS_REVOKED_BEFORE`; the cookie `ds_pilot_access` `HttpOnly`, `SameSite=Strict`, `Path=/dashboard`, `Max-Age=43200`, `Secure` for HTTPS or production. The gate fails closed: unconfigured means 503, never the synthetic profile.
- **One shared limiter key, `'local'`.** No client-written address header is read, because on loopback every request comes from 127.0.0.1 and `X-Forwarded-For` holds whatever the client writes. The cost is a stated limitation: five wrong attempts from anyone lock everyone out for up to fifteen minutes.
- **Ratified from Task 3:** a refused browser gets a relative 303 to `/pilot-access?reason=refused|limited|unconfigured`, while a script keeps the status with a one-key JSON body; attempts take turns on the limiter; a 429 or 503 is not counted.
- **Amended in Task 4:** every page rendered for a verified session (the record and the unservable-profile refusal) shows the session expiry and the topbar's Sign out; the gate's own refusals never do.
- **Task 6's wording** was accepted by the user after the parent's fixes F1–F5.
- **The user's decisions on the final review** (2026-10-20 ~20:15Z, refined in their own words, quoted in `sdd/final-fix-brief.md`):
  - I1: the 503 body is "Pilot access is not configured on this server." followed by the validated problem sentences, one per line, naming variables and never values; status 503 and the cache headers unchanged.
  - D14: a revocation instant later than the request time is invalid configuration, judged by one rule (`readAccessConfigAt`) at one captured request time in both the access decision and the sign-in handler: 503 naming the variable, and no cookie. An equal instant is valid: sessions issued at it are allowed, earlier ones revoked. The time problem is listed beside any other problem, so one refusal still reports every problem.
  - m4: the coverage footnote is worded as definitions, in the user's text, its second sentence later corrected by the user to "For regimes with a knowledge pack, the adjacent count shows how many requirements have reviewer signatures."; the counts and statuses stay derived, and the classification is unchanged.
  - m9: five leftover phrases corrected in the user's wording, and the removed phrases guarded as specific phrases, never as bare words such as "monitoring" or "maintain".
  - I2 is documented for 1a (a generated secret, README; design §5); stronger key derivation belongs to 1b or 1c.
- **The user's instructions for the demonstration** (2026-10-20 ~21:45Z and 2026-10-21 ~06:25Z): response logging may not disclose credentials even when the application fails (headers validated before printing, bodies never printed raw, a guard on every derived line); the configured run requires the pilot-profile marker and rejects the synthetic one, with no profile content in the logs; the issued token is captured before the sign-in response is printed, and only its session `Set-Cookie` value is exempt from the leak scan; the server runs from the verified isolated installation with the agreed external profile path (the SAP SE profile is never copied), started by the user with deterministic commands that unset what must not be set; the served copy stays frozen during the demonstrations; batch 2 and the footnote correction are accepted as saved verification evidence.

## Limitations

Design §5 states them in full. In short: one shared limiter in process memory (five wrong attempts from anyone lock everyone out for up to fifteen minutes; it empties on restart or reload); Next's `localhost` normalisation in middleware redirects and host-bound cookies; sign-out clears one browser only; the fast key derivation (offline guessing from a captured token, minting by a passphrase holder, a future issue time accepted); loopback cookies not scoped by port; a cross-site form post can spend the limiter or sign a browser out; a local `next start` sets `Secure` over plain HTTP, which Safari may refuse; the page's own refusals are HTTP 200 and rely on Next's dynamic-rendering cache headers, and an allowed page reaches the client with Next's `no-store` rather than the middleware's `private` and `Vary: Cookie` (design §2); the gate is temporary (accounts in 1c); "monitored" cannot be earned before Stage 3's scanner; the contact form stays hidden until an inbox is configured.
